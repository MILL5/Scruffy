# November 10, 2026 verification (0.6.0)

Scope: everything in 0.6.0. Scan eligibility and speed, duplicate cleanup, the protected original, saved settings, recovery-journal pruning, the scan stall recorded on November 9, layout and text size, platform support, and acceptance on a real home folder. Written before the release script ran; signing and notarization results are not part of this record.

## Automated

- Full suite: **189 tests passed** (69 app, 120 core), no failures, skips or compiler warnings, on macOS 27.2 with Swift 6.4.2. The total before this work was 165.
- Debug and release builds are clean with the deployment target at macOS 26. `scripts/build-app.sh` produced an arm64 app, version 0.6.0 build 8, `LSMinimumSystemVersion` 26.0, which passed strict deep signature verification. The CI workflow now names the `macos-26` runner; its first run is the pull request for this change.
- The documentation checker passed 82 local references across 18 files, and the website's structured data parses.

## Scan eligibility

- **Same-volume rule.** A test mounts a 4 MB HFS+ disk image inside the fixture home's Downloads folder. The file on it and the mount point are rejected, a chosen folder on that volume yields no files and a "Skipped protected location" note, and a candidate pointing at it fails location validation. With the device comparison removed the test fails on four assertions, so the earlier build accepted such a folder. The enumerator did not descend into the mount point from its parent even before this change; the exposure was a chosen folder on the mounted volume.
- **Cloud placeholders.** Files and folders carrying `SF_DATALESS` are rejected before they are listed, hashed or entered. Only the flag test is unit-tested: the flag cannot be set on a fixture without system privileges, and no real placeholder was scanned.
- **Folder boundaries.** A slash next to a combining mark is one Swift character. A test covers a symlinked folder, `node_modules`, an app bundle, `.ssh`, `Library/Mail` and a folder directly inside Library, each holding a file whose name starts with a combining mark, plus a symlink whose name ends in a prepending mark. All are rejected; an ordinary file with such a name in Documents stays eligible. The same test failed on eight assertions before the path walk split on the slash byte.
- **Large files.** The threshold is 500,000,000 bytes. A sparse file of exactly that size is listed; one byte less is not.
- **Permission notes.** A fixture folder with mode 000 produces one "No permission to read" note and a count of one.

## Speed

- **Folder walk.** On 50,000 one-byte files in 200 folders (debug build, three runs each), the per-file safety check went from 311–379 µs to 92–94 µs and the whole walk from 20.5–25.3 s to 7.5–7.7 s. One Mac under other load; not a real-home benchmark.
- **Duplicate cleanup reads.** The whole-batch pass no longer reads file contents. A test changes an original's bytes while preserving its fingerprint: the batch pass approves the copy, the move-time check skips it, nothing moves and no recovery record is written.
- **Browser-running check.** See the real cleanup below. One check from a background task took 15 ms before and 0.45 µs after (5,000 calls). A stand-in app carrying Firefox Nightly's bundle identifier was seen 0.16 s after it was launched and dropped 0.02 s after it was killed. No real browser was launched or quit for this, and a browser-cache cleanup has not been timed since the change.

## Protected original, settings, restore

- Tests cover a filed copy winning over an older Downloads copy, the oldest winning when every copy is in Downloads, "Keep this copy instead" swapping the protection, the choice surviving later scan results and a cleanup refresh, its reset on changed settings, refusal while the group is being cleaned, the choice still landing when its publication is overtaken and the overtaking one cancelled, and the Trash service moving the previous original while refusing the chosen one on its own.
- Scan options round-trip through an isolated defaults suite. Saved folders that are missing, outside the home folder, inside Library or symbolic links are left out on load. A model without a settings store reads and writes nothing.
- Restoring one record puts the file back and leaves results, selection and scan state as they were.

## Recovery journal

- Compaction keeps the same records in the same order, in one line per live record plus one removal line per removed legacy record; the legacy file's bytes are unchanged; a leftover from an interrupted run is replaced; a log with a malformed committed line is not rewritten; a legacy-only history gets a log only when a record is dropped.
- Two instances appending 200 records while a third compacts 60 times lose nothing and report no error.
- Tidying drops a record whose Trash item is gone, one whose file was put back, and an interrupted move whose original is untouched. It keeps a file still in Trash, an interrupted move whose original is gone, and a record whose Trash folder is missing. The kept file is still restorable afterwards.
- A model that does not load history never tidies. The effect of launch-time tidying on the real journal was not measured: no copy of it was taken before the new build first opened.

## The November 9 scan stall

- **Without the permission question.** A metadata-only walk of the whole real home folder (duplicates off, so no file contents were read) covered 359,618 files in 87 seconds. No single folder-listing call waited as long as 0.2 seconds. The test process inherits its host's Full Disk Access, so macOS asked nothing.
- **With it.** A throwaway app with its own bundle identifier and no permissions listed `~/Documents`, then `~/Desktop`, with the scanner's enumerator options. Both times `nextObject()` returned nothing until the macOS prompt was answered, about 2.7 seconds later. For Documents, `tccd` logged the access request at 15:42:52.785, the user notification, and the response at 15:42:55.468. For Desktop, a one-second sample taken during the wait had all 881 samples in `-[NSURLDirectoryEnumerator nextObject]` → `_URLEnumeratorGetNextURL` → `_GetDirectoryURLs` → `__open`. That is the stack shape recorded on November 9.
- The prompt was answered by the person at the Mac each time, so an unanswered prompt lasting minutes was not observed; nothing in the mechanism bounds the wait. System logs from November 9 were no longer available, so that day's stall is explained by reproduction, not by its own log.
- The fix is visibility, not avoidance. `ScanActivity` is unit-tested, and the footer message was rendered offscreen. It was not seen in the real app: the real scan's folders opened without a wait.
- The probe app is deleted. `tccutil` could not find its bundle identifier afterwards, so its two answers (Documents, Desktop) for `com.richcrane.scruffy.stallprobe` may still be listed under Privacy & Security.

## Layout and text

- Offscreen renders with invented files at 1280×800, 760×560 and 1300×700, light and dark: the category summary line replaces the chart card inside a category and leaves room for one more row at 760×560; row, sidebar and footer text is 11–13 pt; the waiting message and the Full Disk Access line fit.
- The first real-window capture showed the sidebar's selection label cut off beside five-digit file counts. The label now drops its size before it truncates; a render with 28,755 and 5,663 files and a 12,000-file selection shows no cut-off text. This fix was rendered but not seen in the real app.

## Real-machine acceptance

- The packaged 0.6.0 app was launched with two saved folders, Downloads and a fixture folder, written to its defaults beforehand. It scanned both: 1 minute 29 seconds, 40,230 files ready to review and 80 videos.
- A capture of the app's own window showed the three fixture duplicates with the copy outside Downloads marked as the original although the Downloads copy was older, modified dates in each row, and the Full Disk Access line with its button (57 locations refused).
- A browser-cache cleanup of 5,663 files (249.7 MB) ran in that app. It was started in the app by the person at the Mac, not by the agent. Its saved timings: browser-running check 102.1 s for 5,664 checks, batch safety pass 2.2 s, move-time recheck 4.2 s, recovery records 2.4 s. That measurement led to the browser-check change above.
- Driving the window by script was abandoned. Accessibility does not expose the SwiftUI list's rows, and the person at the Mac was using it. One scripted click was sent to a checkbox position while the view may have changed; the app showed nothing selected afterwards.
- The remaining steps ran through the app model in a one-off test process against the real home folder, the real Trash and the real recovery journal, on three fixture files created for the purpose. The scan found the group and protected the copy outside Downloads. "Keep instead" moved the protection. Cleaning the Downloads copy moved it to `~/.Trash` with a job-tagged record. Undo put it back with an identical fingerprint and removed the record. The fixtures were then deleted and the saved folder list set back to Downloads.
- Not done by anyone in the real window: choosing "Keep this copy instead" from the context menu, and pressing the Full Disk Access button.

No personal file was selected, moved or restored by the agent. The only files the agent moved to Trash were its own fixtures.
